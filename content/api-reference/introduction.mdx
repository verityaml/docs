title: API reference
description: Authentication, request/response conventions, and error handling for the Verity REST API

All API endpoints live as Next.js API routes at `/api/`. There is no separate backend server.

## Authentication

Every protected endpoint requires a valid BetterAuth session. The session is established via cookie-based authentication after login.

```
Browser → POST /api/auth/sign-in → Session cookie set
       → Subsequent requests include session cookie automatically
```

API routes extract the session and organization context:

```typescript
const session = await getSession()    // Returns null if not authenticated
const orgId = getOrgId(session)       // Extracts active organization ID
```

All tenant-scoped queries filter by `orgId` for multi-tenant isolation.

## Request format

### JSON body

POST and PATCH endpoints accept JSON request bodies:

```bash
curl -X POST /api/obligations \
  -H "Content-Type: application/json" \
  -d '{"type": "regulatory", "examiner": "FDIC", "responseDeadline": "2026-03-15"}'
```

### File uploads

Evidence and document upload endpoints accept `multipart/form-data`:

```bash
curl -X POST /api/obligations/OB-2026-001/upload \
  -F "file=@request-letter.pdf"
```

Maximum file size: 50 MB. Allowed types: PDF, DOCX, XLSX, CSV, PNG, JPG.

### Query parameters

GET endpoints use query parameters for filtering and pagination:

```bash
GET /api/knowledge-base/browse?domain=bsa_aml&limit=20
GET /api/remediation-items?status=open,remediation_in_progress
GET /api/evidence?sourceType=examination&limit=50&cursor=2026-03-20T10:00:00Z:uuid
```

## Response format

### Success

```json
{
  "data": {
    "obligation": {
      "id": "OB-2026-001",
      "name": "Q1 BSA Examination",
      "status": "in_progress"
    }
  }
}
```

List endpoints wrap results in a named array:

```json
{
  "data": {
    "obligations": [...]
  }
}
```

### Errors

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Obligation not found"
  }
}
```

## Pagination

List endpoints use cursor-based pagination with composite keys to handle timestamp collisions:

```bash
GET /api/evidence?limit=50&cursor=2026-03-20T10:00:00Z:550e8400-...
```

```json
{
  "data": {
    "evidence": [...],
    "nextCursor": "2026-03-19T14:00:00Z:660f9500-..."
  }
}
```

When `nextCursor` is present, more results are available.

## Status codes

| Code | Meaning |
|------|---------|
| 200 | Success |
| 201 | Created |
| 400 | Bad request — validation error or missing required fields |
| 401 | Unauthorized — no valid session |
| 403 | Forbidden — archived resource or insufficient permissions |
| 404 | Not found — resource doesn't exist or doesn't belong to your org |
| 409 | Conflict — duplicate resource or invalid status transition |
| 500 | Internal server error |
| 503 | Service unavailable — background service unavailable |

## ID formats

Verity uses human-readable IDs for top-level entities and UUIDs for child records:

| Resource | Format | Example |
|----------|--------|---------|
| Obligation | `OB-YYYY-NNN` | `OB-2026-001` |
| Compliance program | `CP-YYYY-NNN` | `CP-2026-001` |
| Compliance domain | `CD-YYYY-NNN` | `CD-2026-001` |
| Scoring criterion | `SC-YYYY-NNN` | `SC-2026-001` |
| Score snapshot | `SNAP-YYYY-NNN` | `SNAP-2026-001` |
| Score change event | `SCE-YYYY-NNN` | `SCE-2026-001` |
| Remediation item | `REM-YYYY-NNN` | `REM-2026-001` |
| Request item | UUID | `550e8400-e29b-41d4-...` |
| Evidence | UUID | `550e8400-e29b-41d4-...` |
| Evidence link | UUID | `550e8400-e29b-41d4-...` |

Human-readable IDs are globally unique across all organizations.
