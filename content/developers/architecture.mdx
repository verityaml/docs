## Current production stack

Verity runs on **AWS** — ECS Fargate (compute), RDS PostgreSQL (database), S3 (file storage), SQS + Lambda (background jobs), with Voyage AI for embeddings, Anthropic Claude for document parsing, and SES for email. Deployed via GitHub Actions with a staging-first pipeline gated by E2E tests.

Click any service box for details. See the [AWS migration plan](/developers/aws-migration) for detailed architecture diagrams.

### Service breakdown

| Service | Role |
|---------|------|
| ECS Fargate | Next.js app (standalone Docker), auto-scaling |
| RDS PostgreSQL | Database with pgvector, managed backups |
| S3 | Evidence files, exam uploads, reports (50MB max) |
| SQS + Lambda | Background jobs (parse, auto-match, evidence propagation, backfill, connector sync) |
| CloudFront | CDN with WAF |
| Voyage AI | voyage-law-2 embeddings (1024-dim), legal domain |
| Anthropic Claude | Document parsing via Anthropic API |
| unpdf | Deterministic PDF text extraction (reference-based parsing) |
| SES | Transactional email (password resets, invitations) — IAM-based |
| GitHub Actions | CI/CD pipeline: staging deploy, E2E gate, production deploy |

### Request flows

```
Page load:    Browser → CloudFront → ALB → ECS → proxy.ts (cookie check) → Server Component → Drizzle → RDS
Static asset: Browser → CloudFront (cached)
API call:     Browser → CloudFront → ALB → ECS → API route → BetterAuth session → Drizzle → RDS
Background:   API route → SQS → Lambda → Voyage AI / Anthropic / RDS / S3
Nightly:      EventBridge → Lambda (full-recompute) → RDS (drift correction)
```

## System overview

Verity is a **monorepo with three packages**. The `backend/` package is a shared library (Drizzle schema, config, background jobs, utilities). The `desktop/` package is a Tauri v2 macOS app. All HTTP endpoints live as Next.js API routes inside `frontend/src/app/api/`. The packages share types and config at build time via npm workspaces.

**Key constraint:** LLM usage is classification and retrieval only. Never generation of compliance content. All AI outputs require human review.

## Monorepo structure

```
verity/
├── frontend/          # Next.js app — pages, API routes, components, tests
│   └── src/
│       ├── app/       # App Router (pages + API routes)
│       ├── components/
│       ├── lib/       # Auth, storage, utilities
│       └── proxy.ts   # Session gate (replaces middleware.ts in Next.js 16)
│
├── backend/           # Shared library — schema, config, jobs, utilities
│   └── src/
│       ├── config/    # REGULATION_CONFIG — single source of truth
│       ├── db/        # Drizzle schema, migrations, seed scripts
│       ├── jobs/      # Lambda job functions + shared helpers
│       ├── queue/     # SQS dispatch abstraction
│       └── lib/       # Embeddings, knowledge search, storage, document-model
│
├── desktop/           # Tauri v2 desktop app (macOS)
│   ├── src-tauri/     # Rust source, Tauri config, capabilities
│   └── package.json
│
├── infra/             # AWS CDK infrastructure
│   ├── lib/           # Stack definitions (pipeline, app resources, config)
│   └── cdk.json
│
└── docker/            # Production Docker build
```

Frontend imports backend via workspace aliases:


## Authentication

Verity uses **BetterAuth** (self-hosted, not Supabase Auth).

### Session flow

```
Browser → proxy.ts (cookie presence check, fast path)
       → (dashboard)/layout.tsx → requireAuth() (full session validation)
       → API route → getSession() + getOrgId() (extract org from session)
```

`proxy.ts` only checks that a session cookie exists — no token verification. Full auth happens in the dashboard layout's `requireAuth()` server call. This keeps the proxy fast.

### Organization lifecycle

After signup, BetterAuth creates a user and organization. The `afterCreateOrganization` hook provisions default compliance programs (one per supported regulation type) and logs an audit event.

## Frontend architecture

### Rendering strategy

Server components by default. Client components (`"use client"`) only for interactivity:

- **Server components** — data fetching, auth checks, layout
- **Client components** — forms, search with debounce, status dropdowns, file uploads, polling

### Route groups

| Group | Scope | Layout |

| `(auth)` | Public | Centered card layout |

## Deployment

### Production (AWS)

- **URL:** `https://app.verityaml.com` (via CloudFront)
- **Staging:** `https://staging.verityaml.com`
- **Build:** Docker multi-stage build → ECR → ECS Fargate
- **Pipeline:** Push to `main` → staging deploy → E2E tests → manual approval → production deploy
- **Infrastructure:** CDK-managed, deployed conditionally via GitHub Actions

### Database

RDS PostgreSQL 16 with pgvector extension. Auto-detects PgBouncer pooler for `prepare: false`.

## Key design decisions

| Decision | Rationale |
|----------|-----------|
| No separate backend server | Next.js API routes are sufficient; shared library pattern keeps schema in sync |
| SQS + Lambda for background jobs | Reliable retries, parallel processing, no external job framework dependency |
| BetterAuth over managed auth | Self-hosted auth gives full control for compliance requirements |
| pgvector in Postgres | No external vector store; semantic search collocated with relational data |
| S3 for file storage | Native AWS integration, no external storage provider |
| SES for email | IAM-based auth, no API key management, scoped to domain identity |
| Regulation config as code | Hardcoded enums prevent drift between DB, API, and UI |
| Human-readable IDs | `EX-2026-001` is meaningful in regulatory context; globally unique |
| Evidence auto-linked (opt-out) | Auto-matching links evidence automatically; users remove incorrect matches. No automated compliance assertions. |
| Server components by default | Reduces client JS, enables parallel data fetching, keeps secrets server-side |
