How evidence flows through Verity — from file upload to scoring criteria. Covers the five pipeline stages, matching logic, and the SQS + Lambda background jobs that power them.

## Core concepts

**Evidence is embedded for scoring.** When evidence is linked to a scoring criterion, it is asynchronously embedded via Voyage AI (`voyage-law-2`) and its novelty contribution is computed by cosine similarity against prior evidence on the same criterion. Evidence files are opaque for matching purposes — all matching is based on the metadata of the things evidence is attached to, not the evidence content.

**Matching is transitive.** If a user attaches evidence to request item X, and item X maps to scoring criterion Y, then that evidence is linked to criterion Y. The system asks "what does this item map to?" and copies the item's attachments along for the ride.

**Three entity types form the pipeline:**

| Entity | What it is | Has embeddings? |
|--------|-----------|-----------------|
| **Request item** | A parsed line item from an examination letter (e.g., "Provide CDD policies") | Yes — generated at parse time |
| **Scoring criterion** | A compliance requirement within a domain (e.g., "CDD program documented") | No |
| **Evidence** | An uploaded file (PDF, CSV, image) | Yes — generated asynchronously via `embed-evidence` Lambda for novelty-weighted scoring |

## Step 1: Examination parsing

When a user uploads a PDF, CSV, or image to an examination, the `parse-examination` Lambda function extracts structured request items.

<Steps>
  <Step title="Download file">
    Download the uploaded file from S3 and mark the upload as "processing".
  </Step>
  <Step title="Parse with Claude">
    For PDFs with `sectionLevels` config (e.g., consent orders), use reference-based extraction: deterministic text extraction via `unpdf`, per-article LLM categorization with short-field schema, and deterministic text reconstruction from DocumentModel. Falls back to PDF vision parsing (`parseWithLlm()`) for scanned PDFs or unrecognized structure. Uses regulation-specific system prompts from `REGULATION_CONFIG`.
  </Step>
  <Step title="Bulk insert items">
    Pre-compute embeddings via Voyage AI (`voyage-law-2`, 1024 dimensions) and KB matches for all items, then insert all items in a single atomic DB statement.
  </Step>
  <Step title="Trigger backfill">
    Dispatch to the `backfill-evidence-links` SQS queue to kick off backward backfill (step 4).
  </Step>
</Steps>

Items use `onConflictDoNothing` for idempotency — at-least-once semantics means the job can retry after successful writes.

The embedding captures the *regulatory meaning* of the item's text (e.g., "Provide your CDD policies and procedures"). This embedding is reused later for cross-obligation similarity matching — it is never regenerated.

## Step 2: Evidence attachment

Evidence can be attached in four ways:

**To an examination request item** — the user uploads a file responding to a specific parsed item. This creates an `evidence` row with `source_type: 'examination'` and a foreign key to the request item.

**To a compliance domain** — the user uploads evidence directly to a domain (e.g., the **Training** pillar) without tying it to a specific exam item. This creates an `evidence` row with `source_type: 'domain_upload'` and a foreign key to the domain.

**To the evidence library** — the user uploads a file directly to the org-wide evidence library. This creates an `evidence` row with `source_type: 'library'` and no parent context.

**Via a connector** — a Google Drive connector sync classifies files and creates evidence with `source_type: 'connector'` and a `connector_file_id` FK.

In all cases, the file is stored in S3. The evidence record is metadata only.

---

## Step 3: Auto-match

Auto-matching links request items to scoring criteria using structured rules. It runs within a single obligation.

For each scoring criterion, the matcher checks every request item using a priority cascade:

1. **Definition key match** (most precise) — the criterion's `definitionKey` equals the item's `scoringCriterionKey`. If both have keys but they don't match, the item is skipped entirely with no fallback.
2. **Regulatory source match** (structural) — both reference the same FFIEC section in the knowledge base.
3. **Category/domain alignment** (broadest) — the item's assigned category corresponds to the criterion's domain (e.g., item is categorized as "training" and criterion belongs to the **Training** domain).

When a match is found at any priority level, **all evidence attachments on that request item** are linked to the criterion via its `linked_evidence` JSONB array. The criterion's `evidence_status` is set to `sufficient`.

This is the transitive link. The matcher never examines the evidence file — it only asks "does this item structurally match this criterion?" If yes, the item's attachments come along.

### Domain upload path

Simpler: every file uploaded directly to a domain is linked to **all criteria in that domain** as suggestions (`suggested: true`). Status is promoted to `partial` only if the criterion is currently `missing`. The user must manually accept or dismiss.

## Step 4: Propagate and backfill

This is where embeddings are used for cross-obligation linking. Two complementary flows handle the two directions:

### Forward propagation

When evidence is uploaded to a request item, the `propagate-evidence` function loads the source item's stored embedding (no new Voyage call), queries all request items on other unarchived examinations using `cosineDistance`, and creates cross-links in the `evidence_links` table for items with similarity at or above 0.82. A maximum of 5 cross-links are created per upload.

### Backward backfill

When a new examination is parsed, the `backfill-evidence-links` function runs the reverse — for each newly parsed item, it finds similar items on existing examinations that already have evidence and links that evidence to the new items.

### Auto-match vs propagate

| | Auto-match (step 3) | Propagate/backfill (step 4) |
|---|---|---|
| **What it matches** | Request items to scoring criteria | Request items to request items |
| **Matching method** | Structured (keys, source IDs, categories) | Semantic (embedding cosine similarity) |
| **Scope** | Within one obligation's program | Across different examinations |
| **Evidence flow** | Item attachments to criteria JSONB | Creates `evidence_links` rows |
| **Threshold** | N/A (exact match or category) | Cosine similarity at or above 0.82 |

## Step 5: Score recomputation

All score changes flow through the canonical `recomputeAndCascade()` helper, which bundles: `recomputeCriterionScore()` → `applyScoreDelta()` → `cascadeProgramScore()` → `emitScoreNotifications()`.

Scoring uses a **novelty-weighted additive model**. Each evidence contribution is computed by cosine similarity against all prior evidence on the same criterion:

```
contribution = 100 × (1 − max_similarity_to_prior)
criterion_score = sum of contributions (unbounded)
domain_score = sum of criterion scores
program_score = sum of domain scores
```

Evidence status is **auto-derived** from criterion score:

| Score range | Status |
|-------------|--------|
| ≥ 100 | `sufficient` |
| 1–99 | `partial` |
| 0 | `missing` |

`recomputeCriterionScore()` acquires a `pg_advisory_xact_lock` per criterion, fetches all linked evidence embeddings (excluding `embedding_status='failed'`), computes novelty-weighted scores with deterministic ordering (by `uploadedAt`, breaking ties by `id`), and derives the evidence status from the resulting score.

Program scores are cached on `compliance_programs.current_score` and updated by `cascadeProgramScore()` after every domain score change. Auto-snapshots are created when the program score changes by more than 5% of the program reference max (with a 1-hour cooldown).

A nightly **full recompute** Lambda (EventBridge, 3am UTC) runs `fullRecomputeAllPrograms()` to detect and correct any score drift, writing correction events only when discrepancies are found. Per-domain failures are caught and surfaced with `failed: true` without aborting the rest of the program.

Score changes also trigger **notifications** via `emitScoreNotifications()` — for deltas exceeding 5% of the domain reference max, threshold crossings at the domain's configured readiness target, and program milestones (50/60/70/80/90% of program reference max). Notification metadata is validated at insert time by a Zod runtime schema.

## Background jobs

Verity uses **SQS + Lambda** for background jobs. Job functions live in `backend/src/jobs/` as shared helpers, with Lambda handlers in `infra/lambda/`. API routes dispatch messages via `sendMessage()`/`sendMessages()` from `@verity/backend/queue`.

All Lambda handlers use the shared `createSqsHandler()` factory, which provides:

- **Zod payload validation** — each queue has a typed schema (e.g., `ParseExaminationPayload`). Invalid messages are logged and discarded (not retried).
- **JSON parse guard** — malformed SQS message bodies are caught before validation.
- **Error recovery** — unhandled exceptions trigger best-effort status resets (e.g., `parseStatus` back to `failed`) so records don't get stuck in a processing state.
- **Cold-start guard** — async `setup()` function runs once per container for Secrets Manager initialization.

Schema definitions use zod v4's built-in `z.toJSONSchema()` for LLM structured output (replacing the deprecated `zod-to-json-schema` package).

### SQS queues

| Queue | Lambda handler | Description |
|-------|---------------|-------------|
| `parse-examination` | `infra/lambda/parse-examination.ts` | Parse uploaded examination letters into request items |
| `auto-match-evidence` | `infra/lambda/auto-match-evidence.ts` | Match evidence to scoring criteria |
| `propagate-evidence` | `infra/lambda/propagate-evidence.ts` | Forward evidence propagation across obligations |
| `backfill-evidence-links` | `infra/lambda/backfill-evidence-links.ts` | Backward backfill when a new obligation is parsed |
| `sync-connector` | `infra/lambda/sync-connector.ts` | Google Drive connector sync pipeline |
| `classify-library-evidence` | `infra/lambda/classify-library-evidence.ts` | Library upload auto-classification |
| `embed-evidence` | `infra/lambda/embed-evidence.ts` | Evidence embedding and score recompute |

### EventBridge scheduled jobs

| Schedule | Lambda | Description |
|----------|--------|-------------|
| 3am UTC daily | `full-recompute` | Nightly full score recompute with drift correction |

### parse-examination

Parses uploaded examination request letters into structured request items with embeddings and KB enrichment. See step 1 above for the full flow. Uses Anthropic API (`claude-sonnet-4-6`) via `@ai-sdk/anthropic` — API key loaded from Secrets Manager via `init-secrets.ts`.

### auto-match-evidence

Matches examination evidence against scoring criteria using the priority cascade (definition key, regulatory source, category). Accepts an `examinationIds` array for batch matching across multiple examinations. Updates scores via `applyScoreDelta()`.

### propagate-evidence

Forward propagation — finds semantically similar request items on other active examinations using pgvector cosine similarity (0.82 threshold). Creates up to 5 evidence links per upload with `auto_applied` status for human review.

### backfill-evidence-links

Backward backfill — when a new examination is parsed, searches all existing evidence from other examinations for matches against the new items. Uses the same 0.82 cosine similarity threshold.

### sync-connector

Connector sync pipeline for external integrations (Google Drive). 12-step orchestrator: load config, decrypt credentials (KMS), per-folder diff/classify/apply cycle, batch score updates, cascade program scores, write sync results. Includes token refresh on 401 and circuit breaker (3 consecutive auth failures disables connector).

### embed-evidence

Generates voyage-law-2 embeddings for evidence files asynchronously after upload. Downloads from S3, extracts text, embeds via Voyage AI, persists the embedding, then calls `recomputeCriterionScore()` for each linked criterion. Voyage errors are classified into transient (re-thrown for SQS retry) vs permanent (marked `embedding_status='failed'`). Embedding shape is validated (length 1024, finite values) before persistence. A `db:backfill-evidence-embeddings` script re-dispatches `pending` evidence rows that missed initial embedding.

### Dispatching from an API route

```typescript
import { sendMessage } from "@verity/backend/queue"

await sendMessage("parse-examination", { uploadId, examinationId, orgId })
```

## Where embeddings live

| Location | Generated when | Used for |
|----------|---------------|----------|
| `request_items.embedding` | Exam parsing (Voyage AI, `inputType: "document"`) | KB enrichment during parse, cross-obligation propagation |
| `evidence.embedding` | After upload via `embed-evidence` Lambda (Voyage AI, voyage-law-2) | Novelty-weighted scoring (cosine similarity against prior evidence) |
| `scoring_criteria.embedding` | At criterion creation via `embedMissingCriteria()` | Library/connector classification matching |
| KB tables (4 tables) `.embedding` | Seed time (`npm run db:seed`) | Semantic search in **Reference Library**, item enrichment during parse |

| Setting | Location | Value |
|---------|----------|-------|

| Vector index type | PostgreSQL | HNSW on `vector(1024)` columns |
